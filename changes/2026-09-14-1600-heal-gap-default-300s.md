# Raise the heal-gap default to five minutes

## Why

The U6 heal rule decides what a sleep/wake cycle does to the transcript: a gap
shorter than `healGapSeconds` with the same input device heals back into the
current session; anything longer closes that session as `interrupted` and opens a
new one. The shipped default was 30 seconds.

Thirty seconds is shorter than almost every real interruption. Closing the lid to
walk to another room, locking the screen for a few minutes, a display sleep
between two halves of the same dictation — each of those clears 30s easily, and
each one therefore splits one sitting into two sessions. The rollover is working
as designed; the threshold is just set below the resolution of normal human
interruptions, so the "interrupted" status stops meaning anything and a single
piece of work arrives as a pile of fragments.

The number was also duplicated in three places — the memberwise init, the decoder
fallback, and `RecordingEngine`'s own init default — with nothing keeping them in
agreement.

## How

`StenoSettings.defaultHealGapSeconds` is now the single source of truth, set to
300. All three previous 30s literals reference it, so an engine built without an
explicit threshold and a settings file written without the key agree by
construction rather than by coincidence.

`HealRule` itself is unchanged. It stays purely functional and takes the resolved
threshold as a parameter; only its doc comments changed, to stop naming a specific
number that had already gone stale once.

## Key Decisions

- **Five minutes, not thirty seconds and not thirty minutes.** Five covers the
  interruptions that are obviously the same sitting (lid closed while walking,
  a short lock, a brief display sleep) and stops short of merging ones that
  usually are not. A gap past five minutes generally does mean the user went and
  did something else, and merging those would make session summaries and topic
  extraction describe two unrelated things at once.

- **No migration for existing installs.** A successful start persists the whole
  settings struct, so every install that has ever recorded already has
  `healGapSeconds` written to disk and keeps the value it has. Raising the default
  only reaches fresh installs. That is deliberate: a value on disk may be a
  deliberate choice, and there is no way to distinguish "the old default was
  written here" from "the user set this on purpose." Existing users who want the
  new behavior can edit `~/Library/Application Support/Steno/settings.json`.

- **The setting is read once, at daemon start.** `RunCommand` passes
  `settings.healGapSeconds` into the engine's `private let healThresholdSeconds`,
  so editing the file takes effect on the next daemon launch, not immediately.
  Left as-is; a live-reload path is a larger change than this one.

- **The threshold also gates the device-change heal path.** Same constant, same
  rule, so a mic that disappears and comes back within the window now heals
  instead of rolling over. That is the same fix for the same reason, so it was not
  given a separate knob.

## Testing

`Models/StenoSettingsTests.swift` (new) pins the constant, the memberwise default,
the decoder fallback for a file written before the key existed, and the fact that
an explicit value on disk is never overridden. It also asserts the boundary the
default produces: 240s heals, 300s rolls over.

`SleepWakeHandlerTests.swift` gains a test that builds a `RecordingEngine` with no
explicit `healThresholdSeconds` and drives a two-minute sleep/wake through an
injected clock. It asserts one session, not two, with `after_gap:120s` on the
post-wake segment. Before the change it failed with exactly the reported symptom:
two sessions, no heal marker.

## What's Next

The daemon reads settings only at launch. If more settings become things a user
would reasonably want to change mid-run, a reload path (SIGHUP, or a
`{"cmd":"reload-settings"}`) would be worth the work; today it is one file read at
startup and a restart to pick up an edit.
